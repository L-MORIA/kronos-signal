# Аудит проекта kronos-signal — 2026-10-25

Полный аудит кода и безопасности в два прохода (второй — этот коммит —
дополняет первый, 6e37e68, и устраняет оставшиеся проблемы). Все
исправления покрыты тестами: `pytest tests/` — 71 тест. Живые
smoke-прогоны обоих режимов (5-min и hourly) выполнены на реальных
данных MOEX ISS после объединения правок.

## Критические баги (исправлены)

### 1. Hourly-режим был сломан целиком — `scripts/run.py`
Ресемплинг, заполнение гэпов и метки будущих свечей были захардкожены на
5 минут независимо от конфига. Первый проход аудита параметризовал частоту
(`RULE` из `resample_to`), но `fill_gaps` продолжал заполнять **все** гэпы —
каждая ночь в hourly-режиме превращалась в ~15 фиктивных плоских свечей,
выходные — в ~48, и до трети контекстного окна модели составлял мусор.

**Исправлено (этот коммит):** `fill_gaps(df, rule, max_gap_bars=3)` —
заполняются только внутрисессионные бреши (≤3 бара), ночь/выходные/праздники
не заполняются. Подтверждено живым прогоном: hourly собирает 500 часовых
свечей и прогнозирует 24 часа; 5-min не раздувается фейковыми свечами.

### 2. Потеря данных при загрузке свечей — MOEX ISS отдаёт ≤500 свечей на страницу
Проверено живым запросом: `/candles.json` возвращает максимум 500 строк
**независимо от `limit`**. Старый код запрашивал `limit=500` за сутки и не
использовал пагинацию → терялась хвостовая часть дня (торговый день MOEX —
540+ одноминутных свечей, вечерняя сессия обрезалась).

**Исправлено (первый проход):** `fetch_candles_range()` — пагинация через
параметр `start`, обратное chunks-сканирование `fetch_multi_day` с окном,
зависящим от `interval` (для hourly — до ~150 дней вместо жёстко зашитых 14).
Этот проход добавил тесты на пустую страницу и сетевые ошибки.

### 3. `sample_from_logits` падал с `top_k=None` — `kronos-source/model/kronos.py` (этот коммит)
Сигнатура по умолчанию `top_k=None`, но `None > 0` → `TypeError` при любом
вызове с явным `top_p` и дефолтным `top_k`. Кроме того, при `top_k > 0`
фильтр делал early return и **молча игнорировал `top_p`**; фильтрация
мутировала входной тензор in-place; `temperature=0` давал NaN-вероятности.

**Исправлено:** `None` нормализуется в 0/1.0, top-k и top-p применяются
последовательно (семантика оригинального HF-гиста), замена на
`masked_fill`, явная ошибка при `temperature <= 0`.

### 4. `KronosPredictor.predict` не валидировал длины временных меток (этот коммит)
`predict_batch` валидировал, `predict` — нет: несовпадение `x_timestamp`
со строками df приводило к невнятным ошибкам глубоко внутри.

**Исправлено:** явные `ValueError` с внятными сообщениями.

### 5. RSS-матчинг: паттерны SBERP были мёртвыми — `rss_market_news.py`
Ключевые слова сравнивались подстрокой (`kw in text`), поэтому regex-паттерны
вида `сбер.?преф` не могли совпасть никогда. Первый проход закрыл
`KeyError` на неизвестных тикерах, но решил исход **порядок** проверки:
новость «сбербанк преф» приписывалась SBER (короткое «сбер» проверялось
первым), и паттерны SBERP по-прежнему не работали.

**Исправлено (этот коммит):** `re.search` + побеждает самый длинный
совпавший паттерн (специфичность, а не порядок); `defusedxml` для парсинга
(поверх byte-скрина DTD из первого прохода).

### 6. Абсолютные пути `C:/kronos-signal/...` — `update_models.py`, `scripts/md_to_docx.py`
Скрипты писали/читали по захардкоженному пути (собственный
`check_portability.py` это детектил как CRITICAL).

**Исправлено:** пути вычисляются от `__file__`.

### 7. `chart_sberp.py` падал на пустом дне
Выходные/праздники → пустой df → падение на `closes.min()`.

**Исправлено:** guard с внятным сообщением и exit(1).

## Безопасность

| # | Проблема | Статус |
|---|----------|--------|
| S1 | **Path traversal через `--ticker`**: значение из CLI попадало в имена файлов (`forecasts/..._{ticker}.json`, `{ticker}-chart.png`) и в URL — `--ticker "../evil"` писал вне целевых директорий | Исправлено: `is_valid_ticker()` — `^[A-Z0-9][A-Z0-9._-]{0,11}$` (первый символ буквенно-цифровой, чтобы не проходили `..`), невалидные тикеры skip'аются в main() с NODATA, `moex_url` бросает ValueError как защита в глубину |
| S2 | Парсинг внешних RSS стандартным `ElementTree` (bandit B405/BXML) | Исправлено: byte-скрин DTD/ENTITY (первый проход) + `defusedxml` (этот коммит, добавлен в requirements) + allowlist схемы `https://` |
| S3 | Скачивание моделей с HF Hub без пиннинга ревизии (supply-chain) | Исправлено (этот коммит): `snapshot_download(revision=<sha>)` — качается ровно тот коммит, чей `lastModified` проверен; даты ответов HF API кэшируются вместо повторных запросов |
| S4 | Секреты | Чисто: скан репозитория и полной истории git — ключей/токенов/паролей нет; `.gitignore` закрывает `.env`, `*.key`, `*.pem`, `credentials*` |
| S5 | `yaml.safe_load`, таймауты на все HTTP, TLS нигде не отключён, `eval`/`exec` отсутствуют, subprocess в лаунчерах — list-args без shell | Подтверждено тестами `test_portability_security.py` |

Bandit после исправлений: только 4 LOW-замечания на `subprocess` в
`desktop_launcher*.py` — ложные срабатывания (фиксированные локальные пути,
аргументы списком, без shell).
